# Отчет по лабораторной работе

## Тема

TFT-анализ сети АЗС и построение интерактивного dashboard на Dash.

## Цель работы

Провести анализ почасовых данных сети АЗС, обучить модель Temporal Fusion Transformer для прогнозирования продаж, сохранить обученную модель и представить результаты в интерактивном dashboard.

## Ход работы

### 1. Изучение задания

Изучена формулировка задания из `_задание/Задание.docx`. По заданию необходимо провести TFT-анализ сети АЗС, обучить модель, сохранить ее для повторного использования, построить прогнозы продаж топлива и сопутствующих товаров, сформировать рекомендации и объединить результаты в dashboard.

### 2. Изучение данных

Изучено описание переменных из `_задание/описание данных.docx`. Для итоговой версии проекта используется уменьшенный CSV `_задание/5stations_data.csv`, в котором ровно 5 АЗС и полный набор почасовых признаков.

Исходные данные решено не изменять. Все новые признаки, агрегаты, прогнозы, метрики и графики сохраняются отдельно в `artifacts/`.

### 3. Выбор инструмента визуализации

Вместо Power BI выбран Python-фреймворк Dash. Это позволяет собрать dashboard в одном Python-проекте и напрямую использовать результаты обучения модели, прогнозы, метрики и рекомендации.

Почему это было сделано:

- все шаги можно хранить в одном репозитории;
- графики и таблицы напрямую читают CSV-артефакты из `artifacts/`;
- после переобучения модели dashboard не нужно пересобирать вручную;
- на одном языке проще поддерживать код, оформление и отчет.

### 4. План моделирования

Основные целевые переменные первой рабочей версии:

- `total_fuel_sales` - суммарные продажи топлива;
- `shop_total_revenue` - выручка магазина сопутствующих товаров.

Позже этот же пайплайн можно расширить на продажи топлива по типам: `sales_AI92`, `sales_AI95`, `sales_AI98`, `sales_DT_EURO`, `sales_DT_TANEKO`, `sales_DT_SUMMER`, `sales_DT_WINTER`.

Для оценки качества модели будут использоваться метрики `MAE`, `MSE`, `RMSE`, `R2`. Для отчетности также будут построены графики actual vs forecast, ошибки прогноза, важность признаков и рекомендации по закупкам.

Пошагово модель строится так:

1. Сначала собирается baseline, чтобы проверить весь поток от данных до метрик.
2. Затем обучается TFT для `total_fuel_sales`.
3. После этого прогнозы и метрики сохраняются в `artifacts/`.
4. В конце dashboard читает эти артефакты и показывает их в удобном виде.
5. Для `shop_total_revenue` в dashboard отдельным блоком показывается прогноз товаров, чтобы магазин не терялся внутри топливного анализа.

### 5. Подготовка структуры проекта

Проект переведен с Power BI на Dash. Удалены старые Power BI-материалы и сгенерированные `derived`-витрины, так как они были сделаны под другой сценарий. Исходные файлы задания в `_задание/` не изменялись.

Добавлены рабочие каталоги:

- `app/` - Dash-приложение;
- `artifacts/` - прогнозы, метрики, рекомендации и будущие веса модели;
- `reports/` - отчет по лабораторной;
- `scripts/` - скрипты обучения и подготовки артефактов.

Что здесь важно по шагам:

1. В `_задание/` лежат только исходные данные, их не трогаем.
2. В `scripts/` лежат программы, которые готовят витрину и обучают модели.
3. В `artifacts/` складываются прогнозы, метрики и будущие веса модели.
4. В `app/` лежит дашборд, который читает эти артефакты.
5. В `reports/` описывается ход работы и итог.

### 6. Baseline-модель

Для проверки полного пайплайна до TFT обучена baseline-модель `HistGradientBoostingRegressor`. Это не TFT, а быстрая модель, которая нужна, чтобы проверить загрузку данных, обучение, расчет метрик, выгрузку прогнозов и работу dashboard.

Файл: `scripts/train_baseline.py`.

Основные функции скрипта:

- `load_data()` - читает `_задание/5stations_data.csv`, приводит `timestamp` к дате и заполняет пропуски в категориальных признаках.
- `split_by_time()` - делит данные по времени на train и test.
- `build_model()` - собирает pipeline из кодировщика категорий и модели регрессии.
- `train_target()` - обучает одну модель для одной целевой переменной.
- `calculate_metrics()` - считает `MAE`, `MSE`, `RMSE`, `R2`.
- `export_feature_importance()` - считает важность признаков через permutation importance.
- `build_recommendations()` - формирует рекомендации по станциям на основе ошибки прогноза топлива.
- `main()` - запускает весь процесс и сохраняет файлы в `artifacts/`.

Порядок запуска baseline был таким:

1. Подключить зависимости через `python -m pip install -r requirements.txt`.
2. Запустить `python scripts/train_baseline.py`.
3. Получить прогнозы в `artifacts/forecasts/`.
4. Получить метрики в `artifacts/metrics/`.
5. Получить рекомендации по станциям в `artifacts/recommendations/`.
6. Использовать эти файлы в dashboard.

Разделение данных выполнено по времени:

- train: данные до 2023-12-01;
- test: декабрь 2023 года.

Полученные метрики на тестовом периоде для продаж топлива:

- `MAE`: 4.9572;
- `MSE`: 108.1029;
- `RMSE`: 10.3973;
- `R2`: 0.9782.

Полученные метрики на тестовом периоде для выручки магазина:

- `MAE`: 34.2291;
- `MSE`: 7333.2463;
- `RMSE`: 85.6344;
- `R2`: 0.9280.

Сохранены артефакты:

- `artifacts/forecasts/baseline_forecast.csv`;

- `artifacts/metrics/baseline_feature_importance.csv`;
- `artifacts/recommendations/station_recommendations.csv`.

### 7. Dash-приложение

Создано Dash-приложение `app/app.py`.

Файл работает так:

- при старте читает исходный `5stations_data.csv`;
- читает прогнозы TFT по топливу и товарам;
- читает метрики TFT;
- строит рекомендации по станциям на основе TFT-прогноза;
- строит интерактивные вкладки и обновляет графики при выборе АЗС.

Dashboard содержит вкладки:

- динамику продаж топлива и выручки магазина;
- структуру продаж по видам топлива;
- структуру выручки по категориям товаров;
- влияние погоды и акций на продажи;
- прогноз продаж топлива;
- прогноз выручки магазина;
- график средней абсолютной ошибки по дням;
- отдельный лист с метриками и графиками ошибок;
- диаграмму отклонения прогноза по станциям;
- рекомендации по выбранной АЗС и таблицу рекомендаций по сети.

Как собирался dashboard:

1. Сначала добавлена шапка с названием проекта и выбором АЗС.
2. Затем добавлены карточки KPI по топливу, магазину и трафику.
3. После этого добавлены вкладки с аналитикой, прогнозами, качеством модели и рекомендациями.
4. Потом графики начали читать TFT-артефакты.
5. Затем интерфейс был стилизован через `app/assets/styles.css`, чтобы сделать его читаемее.
6. После этого лишний переключатель модели был убран и интерфейс оставлен в TFT-only виде.
7. Затем метрики были вынесены в карточки, а графики переведены в вертикальную раскладку.
8. После этого блок признаков и блок качества модели были объединены в одну вкладку.
9. Рекомендации были переписаны на простой язык: увеличить закупку, уменьшить закупку или оставить без изменений.

В верхней панели оставлен один режим работы: TFT-прогнозы по топливу и товарам. Это упрощает объяснение на защите и показывает именно тот путь, который демонстрируется в проекте.

Приложение запускается командой:

```bash
python app/app.py
```

После запуска dashboard доступен по адресу `http://127.0.0.1:8050/`.

### 9. Обучение TFT

После исправления окружения обучена модель Temporal Fusion Transformer для целевой переменной `total_fuel_sales`.

Файл: `scripts/train_tft.py`.

Для ускорения обучения на CPU использован компактный файл `_задание/5stations_data.csv`. Это настоящая TFT-модель, но учебная конфигурация сделана небольшой:

- история encoder: 48 часов;
- горизонт прогноза: 24 часа;
- количество эпох по умолчанию: 8, при необходимости можно продолжить обучение из чекпоинта;
- hidden size: 8;
- данные: последние 6 месяцев 2023 года по 5 АЗС.

В последнем прогоне обучение остановилось раньше лимита по `early stopping`, после чего были сохранены итоговые артефакты.

Порядок обучения TFT:

1. Подготовить `TimeSeriesDataSet` с временным индексом, категориальными и числовыми признаками.
2. Разделить данные по времени: train до декабря, backtest на декабрь.
3. Создать `TemporalFusionTransformer` через `pytorch-forecasting`.
4. Запустить обучение через `lightning`.
5. Сохранить checkpoint, конфигурацию и прогнозы.
6. Отдать эти артефакты в dashboard.

Сохранены артефакты:

- `artifacts/models/tft_total_fuel_sales.ckpt` - веса TFT для топлива;
- `artifacts/models/tft_shop_total_revenue.ckpt` - веса TFT для товаров;
- `artifacts/models/tft_config.json` - параметры обучения;
- `artifacts/forecasts/tft_total_fuel_sales_backtest_forecast.csv` - проверка на декабре для топлива;
- `artifacts/forecasts/tft_total_fuel_sales_future_forecast.csv` - будущий прогноз топлива после 2023-12-31;
- `artifacts/forecasts/tft_shop_total_revenue_backtest_forecast.csv` - проверка на декабре для товаров;
- `artifacts/forecasts/tft_shop_total_revenue_future_forecast.csv` - будущий прогноз товаров после 2023-12-31;
- `artifacts/metrics/tft_total_fuel_sales_metrics.json` - метрики TFT для топлива;
- `artifacts/metrics/tft_shop_total_revenue_metrics.json` - метрики TFT для товаров.

Метрики TFT на backtest-окне:

- `MAE`: 16.9405;
- `MSE`: 814.5950;
- `RMSE`: 28.5411;
- `R2`: 0.8333.

Метрики TFT для товаров на backtest-окне:

- `MAE`: 124.6667;
- `MSE`: 92046.7000;

Вывод по TFT для товаров:

2. Из-за этого TFT обучалась заметно хуже и не обогнала baseline.
3. В dashboard baseline больше не показывается как отдельный режим, чтобы не перегружать защиту.
4. TFT для товаров сохранена как экспериментальный результат и остается в артефактах.

### 10. Разделение backtest и будущего прогноза

В dashboard отдельно показаны:

- проверка на декабре 2023 года: факт против прогноза, используется для расчета метрик;
- будущий прогноз после 2023-12-31: сценарный прогноз без фактических значений.

В dashboard можно выбрать, какой режим показывать:

- только TFT-прогнозы по топливу и товарам.

Для будущих признаков используется сценарий: последняя наблюдаемая неделя переносится вперед, а календарные признаки пересчитываются на январь 2024 года. Это нужно, потому что для будущего периода заранее неизвестны фактические погода, трафик и акции.

### 11. Исправление ошибки checkpoint

При повторном запуске обучения после обновления `torch` возникла ошибка загрузки checkpoint:

- `Weights only load failed`;
- проблема была связана с безопасной загрузкой классов `pytorch_forecasting` в `torch 2.6`.

Исправление было таким:

1. В `scripts/train_tft.py` добавлена функция `allow_checkpoint_globals()`.
2. В нее добавлены классы `GroupNormalizer`, `NaNLabelEncoder` и `QuantileLoss`.
3. Функция вызывается перед `trainer.fit()`.
4. После этого обучение можно продолжать из сохраненного checkpoint без падения.
5. Для этой машины обучение было принудительно переведено на CPU-only режим, чтобы не зависеть от проблемного CUDA-драйвера.
